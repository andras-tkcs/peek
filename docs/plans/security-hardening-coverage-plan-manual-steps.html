Peek hardening: checks only a person can run

The plan fixes the 2026-10 audit findings and raises test coverage to 90%. CI covers almost everything; these three checks need a real browser, a real terminal and, if you have one, a real identity provider. Run them on the feature branch after the last phase merges and before the pull request merges, then paste each report line into the PR.

Before implementation

Nothing to do. No accounts, secrets or consoles are needed before the phases start.

After implementation

1. Browser smoke test

about 20 min
ma1-browser-smoke

CI cannot see how a browser applies the new CSP sandbox together with frame-ancestors 'self', whether cookies reach the page frame, or how toasts read.

  1. Check out the feature branch fix/security-hardening-coverage and start a fresh dev server: 
    git fetch origin fix/security-hardening-coverage
git checkout fix/security-hardening-coverage
mise install
mise run run
    The log prints a one-time setup URL on http://localhost:7700.
  2. Open the setup URL and create the first admin. You land on the dashboard.
  3. Save this as origin.html and upload it from the dashboard with visibility public: 
    <!doctype html><html><body><h1>Origin check</h1>
<script>document.body.append("origin: " + location.origin)</script>
</body></html>
    The success toast shows a link like /p/origin-html-k7m2xq (name plus a random six-character suffix).
  4. Open the page link. The frame shows "Origin check" and origin: null. A blank frame with a console error mentioning frame-ancestors is a failure: note it and stop.
  5. In the browser developer tools, copy the frame's src (it starts with /raw/) and open http://localhost:7700 plus that path in a new tab. The tab shows forbidden (HTTP 403).
  6. On the dashboard, set the page to private, then reload the page link while signed in. The frame still loads. Open the same link in a private window: you are sent to the sign-in page.
  7. Set the page back to public. Open it while signed in and leave a comment; if asked for a name, type Someone Else. The toast reads "/p/… is now public". The comment shows your account name with "✓ signed in", not "Someone Else".
  8. Open http://localhost:7700/dashboard?err=Session+expired.+Call+IT. No toast appears.
  9. Sign in with the same account in a second browser or private window. In the first browser click Sign out other sessions in the dashboard header and confirm. The first browser stays signed in and shows "other sessions signed out". Reloading the second browser's dashboard sends it to the sign-in page.

Report in the PR: ma1-browser-smoke: PASS, or ma1-browser-smoke: FAIL at step N: what you saw.

2. CLI sign-in with a typed code

about 5 min
ma2-cli-login

The device flow spans the CLI, the browser and the approval page; tests cover each side separately.

  1. With the server from check 1 running and signed in, build the CLI and start a login in another terminal: 
    mise run build
./bin/peek login --host http://localhost:7700
    The terminal prints URL: http://localhost:7700/cli-login, a code like ABCD-EFGH and "Never enter a code that someone else sent you." A browser tab opens on the URL (open it yourself if it does not).
  2. Type the code from your terminal into the page and click Continue. The approval page shows the warning, "Requested from:" with 127.0.0.1 or ::1, "Client:" starting with peek-cli/, the request time, and "The token expires after 90 days."
  3. Click Approve. The terminal reports the token was saved. ./bin/peek list lists the page from check 1.
  4. Open http://localhost:7700/dashboard and find the API keys card. A "CLI login" key is listed with an expiry about 90 days from today.
  5. Open an old-style link, http://localhost:7700/cli-login/ABCDEFGH. You land on the empty code form; no code is filled in.

Report in the PR: ma2-cli-login: PASS, or ma2-cli-login: FAIL at step N: what you saw.

3. Real sign-in per OAuth provider

about 10 min per provider
ma3-oauth-login

The new OIDC nonce and userinfo subject checks are tested against fakes only. A real Google, GitHub or OIDC provider confirms valid logins still pass. Skip this check if no Peek you run has OAuth configured.

  1. Deploy a build of fix/security-hardening-coverage to a staging Peek whose base URL is registered as a redirect URI with your provider (see auth-access.md). The sign-in page lists your provider buttons.
  2. Sign out, then sign in with the first provider. You land on the dashboard as your usual account.
  3. Repeat step 2 for every other provider you have enabled. Each one lands on the dashboard.

If a sign-in ends with "OAuth profile lookup failed.", search the server log for oidc nonce mismatch or userinfo subject does not match and include that line in your report.

Report in the PR: ma3-oauth-login: PASS (google, oidc), ma3-oauth-login: SKIPPED (no OAuth configured), or ma3-oauth-login: FAIL provider: log line.
