# Contributing

Peek is a Go-first internal company tool. Contributions should make it easier for one organization or trusted team to run a self-hosted HTML review server with clear admin controls, secure defaults, auditability, backup/restore, retention, and simple operations. Report security issues privately as described in [SECURITY.md](SECURITY.md).

## Product Scope

Treat Peek as internal infrastructure, not a SaaS product. Prefer pragmatic self-hosted workflows over product-growth features. Do not add billing, public tenant onboarding, marketplace concepts, public signup funnels, or broad multi-tenant abstractions unless the project direction explicitly changes.

## Architecture

Keep executable entrypoints thin. `cmd/peekd` delegates daemon behavior to `internal/peekd`; `cmd/peek` delegates CLI behavior to `internal/cli`.

Keep HTTP orchestration in `internal/server`, upload creation rules in `internal/uploads`, persistence rules in `internal/db`, storage backends in `internal/objectstore`, rendering and embedded assets in `internal/web`, and shared data shapes in `internal/models`.

When adding behavior, put the invariant in the package that owns it and test it there. Handlers should translate HTTP concerns into package calls; they should not become the place where storage, persistence, rendering, and validation rules are reimplemented.

## Rendering And Assets

Server-rendered HTML lives in `internal/web/templates/*.gohtml`. Browser CSS and JavaScript used by the app live in `internal/web/assets` and are embedded directly with Go `embed`. CSS is generated: `mise run tailwind` (also run by `mise run build`) downloads the pinned Tailwind v4.3.1 CLI, verifies its SHA-256 and regenerates `internal/web/assets/pines.css`; commit the result. The dashboard and admin pages use Alpine.js (`alpine.min.js`, `dashboard-alpine.js`); the viewer (`app.js`, `bridge.js`) is vanilla JavaScript. Do not add other frameworks or a bundler. If you add a CSS or JS file, add it to `assetManifest` in `internal/web/assets.go` so templates can reference it through `{{asset "name.ext"}}` and immutable cache URLs keep working. The web package tests verify that every embedded asset is represented in the manifest.

Browser JavaScript should stay as small controllers: one IIFE per runtime asset, `"use strict"`, file-local `els` and `state` objects when the controller has meaningful DOM/state, and named helpers grouped by role. Keep fixed template nodes addressed by stable `hn-` IDs, repeated dynamic nodes addressed by classes, and UI matching data in `dataset`. Build dynamic UI with `textContent`, `document.createTextNode`, `document.createElement`, `document.createElementNS`, `DocumentFragment`, and `replaceChildren`; do not use HTML string insertion APIs. Validate both sides of `postMessage`, handle async errors explicitly, keep runtime layout updates in style properties, and do not add a dependency without a concrete need.

The app screenshots live only in `docs/public/assets/screenshots/` and are regenerated with `pnpm gen-screenshots` (needs Chromium and sqlite3). The hero image `docs/public/assets/hero.png` is not generated by that script; replace it by hand when the dashboard look changes. The `assets/` directory at the repository root holds the README logo and demo GIF; it is not part of the embedded dashboard/viewer assets.

## Quality Gates

Install the toolchain with:

```sh
mise install
```

Run the normal local gate before committing:

```sh
mise run check
```

Run `mise run check-full` before opening a PR, and always after touching `internal/server`, `internal/db`, `internal/objectstore`, `internal/uploads` or `internal/backends`, auth, settings, rendering, background workers, concurrency or package boundaries:

```sh
mise run check-full
```

Focused commands are available when iterating:

```sh
mise run fmt-check
mise run vet
mise run test
mise run race
mise run build
```

`check-full` matches CI's `build` job; CI also runs the jobs listed under Tests.

Coverage must stay at or above 95% total and 93% for `internal/server`, `internal/db` and `internal/objectstore` (`scripts/coverage-gate.sh`; override with `COVERAGE_MIN` / `COVERAGE_PACKAGE_MIN` only to test the script). Raise the floors when coverage rises, never lower them.

## Tests

Each suite, its exact command and the CI job that runs it:

- Unit tests: `mise run test` (CI job `build`).
- Race tests: `mise run race` (`build`).
- Coverage gate: `mise run coverage` (`build`).
- govulncheck: `mise run govulncheck` (`build`).
- staticcheck: `mise run staticcheck` (`build`).
- Docker integration: `docker build -t peek-example-contact:ci examples/contact-form && PEEK_DOCKER_TEST=1 PEEK_DOCKER_TEST_IMAGE=peek-example-contact:ci go test -count=1 -run '^TestDockerIntegration' ./internal/backends` (`backend-integration`).
- Example module: `cd examples/contact-form && go test ./...` (`backend-integration`).
- Binaries end-to-end: `mise run e2e` (`e2e`).
- Browser: `pnpm install && pnpm e2e-browser` (`browser`; needs Chrome or Chromium, set `CHROME=` to point at it).
- Docker image: `docker build -t peek:ci .` (`docker`).
- Cross-build: windows and darwin (amd64) vet and build in the `cross-build` job.
- Docs site: see Docs site below (`docs`).
- Release-fixture refresh: `scripts/make-release-fixture.sh v0.10.0`.
- Manual smoke: `mise run run`, then `mise run smoke`.

## Docs site

Install with `pnpm install --dir docs`, preview with `pnpm docs:dev`, build with `pnpm docs:build`, and check links with `node scripts/check-docs-links.mjs docs/dist`. Pushes to main that touch `docs/` are published by `.github/workflows/pages.yml`.

## Pull requests

Name branches `<type>/<slug>` with type one of `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `style`. Run `mise run check-full` first. The required checks are `build`, `backend-integration`, `docs`, `docker`, `cross-build`, `e2e` and `browser`. PRs merge with merge commits only (no squash or rebase), so write each commit message for main's history. A user-visible change adds a line under `## [Unreleased]` in CHANGELOG.md. Fill in `.github/pull_request_template.md`.

## Review Bar

A good change is small enough to review, has a clear owner package, includes tests near the invariant it changes, and does not make internal deployment or operations more surprising. Prefer boring Go, explicit errors, narrow interfaces, and standard library behavior where it fits.
